## 二、CI 判据「假性不通过」根因定位（顺带发现的老问题）

**现象**：产物明明齐全（index=439 / fences=439 / missing=0），CI 仍跑完整 precompute，
多耗 8-15 分钟。

**排查路径**：
1. 纯净检出（`git archive`）复现判据 → **全部通过** → 差异在 CI 环境不在仓库内容
2. 从 git blob 逐个提取 fence hash → 439，与索引条数一致
3. 发现索引里有 **23 个语义名**（`3.2-data-cleaning` 等）+ 1 个重复 value
   （`20.1-monty-hall` 出现 2 次，故 439 条 → 438 唯一名），但 MISSING 仍为 0
4. 回到 YAML 看出根因：判据用两段 `python3 -c ...`，失败时被 `|| echo 0` / `|| echo 999`
   **静默兜底** → python3 异常时 INDEX_N=0 / MISSING=999 → 判据「假性不通过」，
   而「不通过就跑 precompute」被当成常态，真实原因被彻底掩盖

**修法**：新立 `scripts/check-precompute-ready.mjs`（Node 一次算完三个数，
Node 是 CI 既成依赖不会缺；任一环节失败**显式报错并非 0 退出**，不再静默兜底），
CI 第 6 步改调它，判据数字写入 **job summary**，解析失败显式 exit 1。

## 三、`tests/_audit-live.mjs` 两处缺陷（实测踩到才发现）

   **把已算完的 120 页核验结果一起带崩**（只看到一句异常，没看到结论）
   → 改用带时间戳的独立目录（不删旧目录）+ 清理失败不崩

## 六、踩坑记录（环境类，非代码缺陷）

- **`python3` 在 CI 的静默兜底**：`|| echo 0` / `|| echo 999` 把失败伪装成合法数字，
  是「假绿/假红」的典型来源 —— 判据脚本失败必须**显式报错非 0 退出**
- **safe-delete 批量保护阈值 50**：超过 50 个文件的 `fs.rmSync(recursive)` 会抛错，
  `node fs.unlinkSync` 同样被拦。批量清理用 `mv` 移出工作区（同盘秒完）
- **safe-delete 拥堵会连带影响其他命令**：`git status` / `ls` 也会 SIGTERM 挂起 →
  换 PowerShell 工具验证
- **308 重定向**：Cloudflare Pages 规范形式会让裸请求拿到空响应
