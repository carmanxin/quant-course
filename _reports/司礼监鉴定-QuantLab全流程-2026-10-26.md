### 3.2 预计算层（precompute-py-outputs.mjs）—— 主体可靠，但有一处杀器

**判定逻辑是逐层兜底的，写得极其用心**（`precompute-py-outputs.mjs:960-1040`）：

```
scaffoldOnly  → 拒绝"只有标题没有结果"的假输出
wrappedIsFatal → NameError/缺模块 一律降级为 note，绝不展示裸 traceback
hasUsefulText  → 文本须 > 30 字符才算实质输出
hasVisual      → 有图即算有产出
```

**结果分布**（583 个 output.json，按索引覆盖的 439 块计）：

| 类别 | 数量 | 说明 |
|---|---|---|
| 真实运行输出 | **227（51.7%）** | 含 24 个"自动调用 demo 数据"——经核为**真实执行**，非伪造 |
| note 回落说明 | 201 | 诚实标注"无法独立运行"及其原因 |
| error | 0 | 索引覆盖部分零错误 |
| 无产物 | 11 | — |

note 回落原因分布：**275 个（86.8%）为"仅函数/类定义，无运行入口"**。
此为诚实之表态，非欺瞒——但同时指出：**这 275 块中有相当部分具备 demo 化空间**（`genDefCallLines`/
`demoArgExpr` 机制已具备），是提升真实输出占比的最大未开发矿脉。

**⚠ 杀器：重跑会覆盖既有优质产物**

实测以 `PRECOMPUTE_ONLY=6136496a` 重跑单一 fence，**原本 608 字符的真实运行结果被覆写为空 error 产物**。
此非理论风险——`precompute-py-outputs.mjs:1038` 处 `writeFile` **无"新结果质量劣于旧结果则保留旧产物"的保护**，
任何一次失败重跑都会静默降级既有成果。（本次已用 `git checkout` 复原，见第五节。）

### 3.6 CI 与部署（.github/workflows/deploy.yml）—— 有一处逻辑悖论

**先扬后抑。** 该 workflow 设计相当考究：
- 明确「平台不得自行构建」（EdgeOne/CF 容器无 Python → 439 个案例结果全丢），改由 GitHub Actions 构建后分发；
- 双通道部署（EdgeOne Pages 主 / Cloudflare Pages 灾备）+ `dist` 分支保底；
- `pip cache` 被刻意禁用并写明原因（setup-python Post 步骤在无缓存可存时会把 job 拖成 failure）——
  **这是踩过坑才写得出的话**；
- `requirements-ci.txt` 精简至 ~400MB，与根目录 3GB+ 的 `requirements.txt` 分离，注释写明取舍。

**⚠ 阈值悖论**：`deploy.yml` 以 `ls public/code/*.output.json | wc -l >= 480` 判定是否跳过 precompute。
而：

```
唯一 fence 数（precompute 产出上限）= 439
CI 判定阈值                        = 480
当前仓库实际文件数                  = 583
```

**439 < 480 —— 一轮全新 precompute 永远达不到阈值。** 现有 583 中有 **145 个是孤儿产物**
（存在但 `_index.json` 未引用，其中 40 个还带真实输出）。换言之：
**CI 之所以"跳过 precompute"，靠的是孤儿产物凑出来的数字，而非逻辑本身成立。**
一旦清理孤儿产物，阈值立即跌破，CI 转入 20 分钟慢路径；若有人为提速上调阈值，
则 precompute 在 CI 中**永久成为死代码**——而 CI 恰恰是「改了 md 后唯一能重建结果」的地方。

## 四、奉旨三道整饬令（按轻重缓急）

### 🔴 第一令 · 堵住产物覆盖漏洞（**最高优先**）

**问题**：`precompute-py-outputs.mjs:1038` 无条件 `writeFile`，失败重跑会降级既有优质产物。

**方略**：写入前比对新旧质量，**新结果劣于旧结果则保留旧产物**。
判定沿用文件内既有的 `hasRealOutput` / `hasUsefulText` 语义即可，无需引入新标准：

```js
// 伪代码示意
const oldPayload = await readIfExists(outPath)
if (oldPayload && !isBetter(newPayload, oldPayload)) {
  return { name, file, kept: true }   // 保留旧产物，不降级
}
await writeFile(outPath, JSON.stringify(newPayload, null, 2))
```

**验收**：重跑 `6136496a`（默认 30s 超时必失败）后，产物 text 仍为 608 字符，不被清空。

### 🔴 第二令 · 修正 CI 阈值悖论

**问题**：480 阈值 > 439 产出上限，判定逻辑不成立，实际靠孤儿产物凑数。

**方略**（择一）：
1. **改判据为「索引完整性」**——以 `_index.json` 条目数（439）为准，
   `== 439` 即视为产物齐全，跳过 precompute。判据与产出能力自洽。
2. **保留阈值但下调至 ≤ 439**（如 400），并同步清理 145 个孤儿产物。
3. **保留现状但补注释**，明写「阈值基于历史产物计数，包含已废弃的孤儿产物」。

**强烈建议采 1**——判据自洽才能长期免维护。孤儿产物顺带清理，
`_index.json` 未引用者本无保留价值（其中 40 个带真实输出的可先比对是否有对应 hash 再决定）。

### 🟡 第三令 · 订正文档与清理死代码

| 项 | 现状 | 应改为 |
|---|---|---|
| `DEPLOY.md:54` | 「89–104 秒」 | **实测 1098 秒（18.3 分钟）**；并复核 CI `timeout-minutes: 45` 是否够用 |
| `DEPLOY.md:48` | 「503 个预计算产物」 | 实际 **583** |
| `DEPLOY.md:184` | 「4012 个文件」 | 实际 **1193** |
| `requirements-ci.txt` 注释 | 「覆盖全站 503 个代码块」 | 实际 **439** 个 fence |
| `.vitepress/config.ts:308-405` | QuizBlock 转换逻辑 | 组件已删，**逻辑成死代码**，应删或恢复组件 |
| `precompute-py-outputs.mjs` | `pip install` 全局自动装包 | 违反包隔离原则，且 CI 中不可控；建议改为 `PRECOMPUTE_INSTALL=1` 显式开启（**代码已有此开关，注释未同步**） |

**附带**：`.vitepress/` 下积 **12 个** `dist_old_*` 目录、`portable/` 下 **9 个**，
每个约 70MB，合计逾 **1.4 GB**。均未被 git 跟踪（`.gitignore` 已覆盖），但占盘显著，建议择机清理。
